# First-principles bounds on sandbox density

*This page answers a question the candidate search cannot answer by itself: how would we know that the search has gone far enough, and that the composed scheme is the most efficient one available? The answer is an upper bound. For each resource the server has, the per-sandbox consumption has a floor set by the workload and the service level, taken optimistically over the widest class of mechanisms the isolation floor permits; the density no scheme can exceed follows from those floors; and the composed scheme is measured as a fraction of it. Where the fraction is close to one, further search cannot help. Where it is not, the gap names what a further candidate would have to do. Every symbol and default value is from [`benchmark/README.md`](benchmark/README.md) unless defined here; every derived number was recomputed from the formulas on this page. The write-and-revise loop that produced it, with each review's findings, is logged in [`BOUNDS_LOG.md`](BOUNDS_LOG.md).*

## 1. Density as a minimum over resources

A server holds `D` sandboxes when every resource suffices for all of them. With five resources, DRAM `M`, cores `C`, storage bandwidth `B`, storage endurance `E` and storage capacity `S`:

```
D = min(D_mem, D_cpu, D_bw, D_end, D_cap)

D_mem = M / (a · m_act + (1 − a) · m_idle)
D_cpu = C / (a · c_act + (1 − a) · c_idle)
D_bw  = u · B / (ω · (s_evict + s_wake))
D_end = E / (ω · s_evict)
D_cap = S / s_store
```

`a` is the fraction of time a sandbox is active; `m_act`, `m_idle` its DRAM in each state; `c_act`, `c_idle` its CPU in each state (in cores); `ω` its wake rate (wakes per second per sandbox, `ω = a / T_act` for bursts of mean length `T_act`); `s_evict` the bytes written to storage per idle period and `s_wake` the bytes read per wake; `u` the utilization at which the drive is run (a queue at `u` = 1 is unstable, so a bound is taken at `u` = 0.9); `E` the drive's rated write rate over its life (drive writes per day, DWPD, times its capacity); `s_store` its state on storage. The first three drafts of this page omitted endurance; at this workload it binds before bandwidth does. An **upper bound** on density comes from replacing every per-sandbox quantity by its **floor**, the least any mechanism could consume for this workload at this service level. Each floor is taken over the widest mechanism class in its own resource (the CPU floor is a native process; the kernel-state floor assumes a kernel per tenant), so the bound on `D` is valid even where no single mechanism attains every floor at once: the minimum over per-resource floors is at least any one mechanism's minimum. The bound is not a design; it is what no design can beat.

Defaults, from the benchmark page: `M` = 921,600 MiB, `C` = 128 (256 shown where it matters), **one NVMe drive**, `B` = 2 GB/s (1,907 MiB/s), `S` = 7.68 TB (6.98 TiB) and a rating of **3 DWPD** (`E` = 254 MiB/s; 1 DWPD is 85 MiB/s), a parameter this page adds; `a` = 0.1, `c_act` = 0.1 core, `T_act` = 60 s so `ω` = 1/600 per second (one wake every ten minutes, a parameter this page adds), `P_proc` = 60 MiB, `F_written` = 100 MiB, `F_public` = 200 MiB, hot set `W_h` = 24 MiB, compression ratio `r` = 2.0. The wake rate of the whole server is `λ = D · ω`: 21.3 wakes per second at `D` = 12,800.

## 2. Floors

### 2.1 Active DRAM

A sandbox doing work must have in DRAM everything its work touches that no other tenant may hold for it. The isolation floor of the Blueprint allows exactly one kind of cross-tenant sharing, read-only pages of public content. The **floor over the permitted class** is therefore the burst's touched set of tenant-private data plus the per-tenant structures that name shared data: paging the cold part of an *active* sandbox is a permitted mechanism, and the model puts a burst's touched set at 24 MiB (REAP's average) everywhere else, so the floor is about **26 MiB** with the kernel and host state of the table below, unmeasured for agents. What the table below states instead is the **model's allocation**, the full `P_proc` and `F_written`, which is what the composition and the baseline rungs both charge; it is the right thing to compare the scheme's 171 MiB against, and it is not a floor.

| term | model allocation, with the per-tenant floor of its shareable part | why | default (MiB) |
|---|---|---|---|
| `P_proc`, the runtime's private heap | all of it (model value; the floor is the burst's touched part) | tenant-private | 60 |
| `F_written`, files the tenant wrote | all of it (model value; as above) | tenant-private | 100 |
| `F_public`, public image content read | the per-sandbox index over shared pages: page-table entries, 8 B per 4 KiB page, 0.2 % (0.0004 % with 2 MiB mappings) | the content is shareable; the mapping that names it is not | 0.4 |
| `K`, kernel state for the tenant's processes | task and address-space structures, the page tables of `P_proc` and `F_written` (0.2 %), socket and file state | a kernel exists per tenant on both sides of the comparison; a few tens of KiB per process, 1–2 MiB for a runtime of a few processes, *estimated* | 1–2 |
| `X`, fixed per-sandbox state in the host | page-table roots and one control structure, tens of KiB | | 0.05 |
| **`m_act`, model allocation with minimal overhead** | | | **161.5–162.5** |

The scheme's warm figure is 171 MiB (`README.md`, model table): `X` 2, `K` 5, `F_public` residue 4 (the tree's 64 B per 4 KiB of per-frame metadata, which the design keeps per kernelet, plus page tables), `F_written` 100, `P_proc` 60. That is **5–6 % above the model's own allocation**: the mechanism adds 9 MiB to what the workload was assumed to need, about 3–3.6 MiB of frame metadata that a design sharing metadata across borrowers would save, 3–4 MiB of `K` (a modeling choice, unverified on both sides), 2 MiB of `X` (C04's estimate against tens of KiB). Since the memory bound never binds on the 128-core server (§3), none of this changes the count there; on 256 cores every MiB of `m_idle` matters and `m_act` enters at a tenth of its weight.

Two workload choices dwarf every mechanism here, and they move the *memory* bound only. Baking a sandbox's dependencies into its image moves them from `F_written` to `F_public`, which is shareable: at `F_written` = 10 the scheme's warm figure is 81 MiB and its memory bound at 500 ms rises from 22,756 to 29,257, **1.3×**, which changes the count only where memory binds (256 cores, or a very idle agent). An agent runtime with a 12 MiB idle heap (`py256`, measured) instead of the model's 60 does the same. The bound is a function of the workload before it is a function of the sandbox.

### 2.2 Idle DRAM

An idle sandbox must hold in DRAM whatever cannot be brought back within the wake bound `W` after a message arrives. The fetch is one sequential read of the recorded hot set plus one random read per page the record missed. On one drive the read of `W_h` = 24 MiB takes 12.6 ms of service time. At `D` = 12,800 the drive's utilization is 0.27 from the wake reads alone or from the eviction writes alone (24 MiB each per cycle), 0.54 with both; the mean M/D/1 queueing delay is 2.3 ms at 0.27 and 7.4 ms at 0.54, and if the host's I/O scheduler serves wake reads ahead of eviction writes (`mq-deadline` or BFQ do; NVMe's default `none` has no preference), the read queue sees a figure between the two, about 4.7 ms in the mean at 0.54 with non-preemptive priority. A tier is a bound on every wake, so the tail matters more than the mean; this page takes the 99th percentile as its service level (at 21 wakes per second that is still 18,000 late wakes a day; the 99.9th percentile at 0.9 is about 405 ms). The 99th-percentile M/D/1 wait is about 22 ms at 0.27, 47 ms at 0.54 and 270–280 ms at 0.9 (exact at the first two, simulated at the third; an M/M/1 tail is 2–2.6× that). This page takes the **fetch of the recorded set as 20 ms in the mean** (12.6 ms of service plus the 0.54 delay) and derives the mean budgets from what the tier leaves after it, with no separate allowance for the agent's own first response, and states the tail beside them. The floor on `m_idle` is then set by the **miss budget**: how many unpredicted pages fit in the remainder at 90 µs per random NVMe read. That is the unloaded latency; the budgets assume misses bypass the bulk queue (NVMe's multiple queues let 4 KiB commands interleave with the pieces of a 24 MiB transfer) at a latency that still rises under load, so they are upper bounds. A compressed pool does not enter the miss budget: it holds the recorded set, and a miss is by definition outside the record, so a pool only shortens the hit fetch (C07's decompression of 24 MiB takes 6–12 ms against 20) and buys roughly 90–150 more drive misses.

| tier | time left after the sequential read (20 ms mean; tail at the stated utilization) | miss budget from NVMe | floor on `m_idle` |
|---|---|---|---|
| ≤ 5 s | 4.98 s | ~55,000 pages (216 MiB, more than the private state) | **0** |
| ≤ 500 ms | 480 ms in the mean; ~440 ms at the 0.54 tail, ~210 ms at the 0.9 tail of the rows between 21,450 and the crossing | ~5,300 pages in the mean (21 MiB); ~2,300 at the 0.9 tail | **0**, if the record misses fewer than about 2,000–5,000 pages |
| ≤ 50 ms | 30 ms in the mean; ~11 ms at the tail with read priority (reads at 0.27 plus the residual of a write in service, p99 about 26 ms), none at 0.54 | ~330 pages in the mean, ~130 at the tail with read priority | **12 MiB** (the hot set compressed, `W_h / r`, fetched in 6–12 ms with no drive read) if the record misses fewer than about 400–500 pages in the mean at unloaded latency; otherwise the compressed miss set as well, unmeasured, toward the model's 99. A floor of 0 from NVMe is not tail-feasible at this tier without read priority, and with it only under about 130 misses |

Two things the floor makes explicit. First, at the 500 ms and 5 s tiers **nothing needs to stay in DRAM**; what the model keeps resident (a 24 MiB hot set, plus the kernel state a guest-side reclaimer cannot evict) is a policy against imperfect prediction and a limit of the cooperative mechanism, not a floor. Whole-kernelet hibernation with a prefetch record (C13's host walk plus C03's record) reaches the floor at 500 ms **only if it is incremental**, writing the dirty kernel and user pages of the cycle rather than the kernelet's whole state, since §2.4 shows a whole-state write per cycle is drive-bound at a fraction of the density; a VM platform reaches the same floor by suspending with a diff snapshot and lazy restore. Both are the same idea and neither changes the ratio between them. Second, at the 50 ms tier the model's 99 MiB is eight times the compressed-hot-set floor, and the VM rungs' 105–203 are nine to seventeen times it, **if the wake record misses fewer than about 400–500 pages**; the model keeps *all* private state in the compressed pool (C07) precisely because it does not assume that. The floor keeps only the hot set there and the rest on NVMe, a **tiered idle state**. Whether the record's misses fit is unmeasured, and this is the tier where it is least likely to: REAP reports its record cuts restore time 3.7×, not to zero, and a few hundred misses is a tight budget. If it does fit on both sides, the tiered policy gives idle figures of about 19 MiB (kernelet: 2 + 5 + 12) and 18 MiB (VM: 6 + 12), which moves both to their CPU bounds on 128 cores and collapses the 50 ms tier onto the 500 ms case (on 256 cores the non-DAX VM stays memory-bound at 17,100). This is a candidate the search had not listed; it is C15 in [`candidates.md`](candidates.md), generic, conditional on its miss rate.

### 2.3 CPU

Active CPU decomposes as `c_act = c_user + c_kernel + c_mech`: the tenant's own user-mode work, the kernel work that work requires, and the sandboxing mechanism's overhead (exits, second-level walks, double zeroing, crossings). The floor is `c_mech = 0`, a native process in a container: **no sandbox platform can hold more sandboxes than the same server holds native processes** of the same workload. `c_kernel` is not mechanism-independent, though: it is the cost of a particular kernel's paths, Linux's for the VM and Asterinas's for the kernelet, and the ratio of the two on this workload is unmeasured and of either sign; the floor takes the cheaper of the two, which makes it partly definitional. Idle CPU has floor `c_idle = 0` (an event-driven idle sandbox consumes nothing until an event), which the kernelet approaches with C06 and a VM approaches to 0.033 % of a core (measured). The CPU of the eviction and wake machinery (writeback, the fault storm on wake, about 0.3–1 core at 12,800) is neglected in the 500 ms and 5 s rows and counted in the 50 ms row; it is under 1 %.

The model applies `c_act` = 0.1 to both sides and C14 treats the kernelet's figure as the reference. The kernelet's own mechanism overhead is unmeasured; taking it as 0–10 % **[unverified]**, the native floor is `0.1 / 1.1` to 0.1 and `D_cpu ≤ 12,800–14,080` on 128 cores, 25,600–28,160 on 256. The CPU ratio between any two sandboxes of this workload is `(1 + c_mech,VM) / (1 + c_mech,kernelet)` times the kernel-path ratio. C14 puts the VM's `c_mech` at 0–30 % for its assumed fraction of fault-heavy work (`f` = 0.1–0.3, unverified; `f` = 0.5 would give 1.5×), so the ratio is **1.0–1.1× at technique parity, times the kernel-path ratio [unverified]**, and up to 1.3× against non-hugepage VMs *for C14's range*, not as a bound. The kernel-path factor is carried through every parity ratio below; a kernel whose paths were several times cheaper than Linux's on this workload would move them, and nothing measured suggests one. This is what stops the composed scheme: once idle sandboxes leave DRAM on both sides, density is CPU-bound on both sides, and CPU has no sandbox-specific floor below native.

### 2.4 Storage bandwidth

Every idle period writes what changed since the last one, and every wake reads what was evicted of the hot set. Both are choices with a large range, and they apply to **both sides of the comparison**. The composed scheme keeps its hot set resident (C03: 24 MiB stay in DRAM at the 500 ms tier), so its wakes read only the record's misses, about nothing in the model, and its drive traffic is the dirty set alone; the first two drafts of this page charged it the hot-set read as well, which double-counted 24 MiB per wake. The 24 MiB dirty set is itself a worst case: it counts every dirtied page as evicted and rewritten each cycle, disjoint from the resident hot set, whereas a dirtied page that stays resident is written zero times, and the pages a burst writes lie inside the pages it touches. The scheme's real writes are between the pages dirtied outside the resident set (possibly near zero) and 24 MiB, so every drive count below is an **upper bound**.

| eviction policy | `s_evict` per cycle | `s_wake` | `D_bw`, one drive at `u` = 0.9 | who does this |
|---|---|---|---|---|
| whole state written at every suspend | 376 MiB (a VM's touched pages) | 24 | **2,570** | Fly.io's suspend (full-memory write); Firecracker full snapshots |
| whole private state, hot set evicted | 165 MiB | 24 | 5,450 | a kernelet hibernated without dirty tracking |
| dirty pages plus the kernel state, hot set evicted | 5 + 24 | 24 | 19,400 | a kernelet hibernated at the 5 s tier with dirty tracking of user pages only |
| dirty pages only, hot set evicted | 24 **[unverified]** | 24 | 21,450 | the `m_idle` = 0 configuration of §2.2, incremental, on either side |
| dirty pages only, hot set resident: **the composed scheme** | 24 **[unverified]** | ≈ 0 | **42,900** | C03 as composed; host swap of a VM with a resident hot set |
| the floor: a burst that dirties little | → 0 | ≈ 0 | unbounded by the drive | an agent that waits on a model |

So the drive's bandwidth binds two things and not a third. It binds any platform that rewrites a sandbox's whole memory per idle cycle, at **2,570** sandboxes on one drive at this wake rate regardless of its DRAM (a throughput bound: at that utilization its 197 ms writes put a wake read's tail in seconds, so the 500 ms tier binds it lower still); it binds a scheme that evicts the hot set and refetches it, at 21,450 on one drive; and it does not bind the composed scheme, whose writes put one drive at `u` ≈ 0.5 at 20,000–23,000. Between the last two lies a trade: evicting a fraction `ψ` of the hot set lowers `m_idle` and raises the drive traffic, and the memory and drive bounds cross at `ψ` = 0.44–0.55, at 27,750–29,770 on one drive, above the 256-core CPU bound's 25,600 and straddling its 28,160; so the CPU bound is reachable, or nearly, on one drive's bandwidth by evicting about half the hot set, and on two drives by evicting all of it. Against the keep-warm rung, which never writes, the drive limits only the scheme.

**Endurance binds before bandwidth.** The same writes wear the drive: 24 MiB per sandbox per ten minutes is 512 MiB/s at 12,800, 46 TB per day, **6.0 drive writes per day** on one 7.68 TB drive, and 10.7 at 22,756; enterprise NVMe is rated at 1–3 DWPD over five years. `D_end = E / (ω · s_evict)` is **6,360 per drive at 3 DWPD** (2,120 at 1 DWPD) for the model's dirty set, 405 (135) for the whole-memory rung, and 12,700 with a compressed pool that halves the bytes written (C07). So the model's server needs **up to two 3 DWPD drives, at the rating, at 12,800 and up to four at 22,756**, or half that with the pool (which costs about one core of LZ4 at 512 MiB/s), or a smaller dirty set; the drive is a consumable that scales with density, and "one drive suffices" is true of bandwidth alone. (Mixed-use 3 DWPD parts are usually the 6.4 TB SKU over-provisioned from 7.68; at that capacity `D_end` is 5,300 per drive.) Wear does not leave the ratios between rungs alone: a rung that writes more per cycle needs proportionally more drives for the same density, so its ratio against the scheme depends on how many drives each side is given. The whole-memory rung is the extreme case: 405 per 3 DWPD drive, 2,570 per drive by bandwidth, so it needs about thirty drives to reach 12,800 where the scheme needs two.

### 2.5 Storage capacity

`s_store ≥ F_written + P_proc` per sandbox, 160 MiB uncompressed, 80 MiB at `r` = 2: `D_cap` = 45,700–91,500 on one 6.98 TiB drive, never binding on this server.

The lower rows answer the question this page was written for. **At technique parity, against a platform that pages out idle sandboxes incrementally, a 5–10× density gain is not reachable by any scheme on this server and workload**, kernelet or otherwise: the bound is 1.1× on 128 cores and 1.8–2.0× (without DAX) or 1.25–1.4× (with DAX) on 256, times a kernel-path ratio that is unmeasured and not credibly a factor of several, because the comparison is CPU-bound on both sides and CPU has no sandbox-specific floor. The target is met where the bound permits it and missed where the bound forbids it.

Storage capacity `s_store` has no row because it never binds (§2.5). Stop-and-start is listed rather than composed because the workload keeps a resident agent whose session state is the point of the sandbox; where it is not, it beats every other 5 s treatment. Two-term interactions that the table does not show were checked separately: compressing *active* memory trades CPU for DRAM at a rate (LZ4 at 0.5–0.7 GB/s per core) that makes it a loss when CPU binds, which it does at every parity cell; far memory (C08) moves the `m_idle` floor rather than the terms and is deferred on hardware. That is the sense in which the search is complete: not that every mechanism has been imagined, but that every term of the bound has been treated in every way the isolation floor permits, and the remaining distance to the bound is in the "what fills the gap" column of §3.

## 5. What would move the bound

Since the composed scheme is within 10 % of the bound on 128 cores at the 500 ms and 5 s tiers and within 27 % on 256, further density comes mostly from moving the bound itself:

- **The workload.** `F_written` → `F_public` by baking dependencies into images (1.3× on the scheme's memory bound, which counts only where memory binds); a smaller resident runtime (`P_proc`); a smaller dirty set per cycle, which moves the wear bound everywhere and the bandwidth bound where the hot set is evicted; a lower `c_act`, which is the agent's, not the platform's.
- **The server.** In the model each resource carries about the following: 100 sandboxes per core (at `a · c_act` = 0.01), 20,000–23,000 per 900 GiB of DRAM (at 40–45 MiB average per sandbox), 21,000 per 2 GB/s drive's bandwidth if the hot set is evicted and refetched (43,000 if it stays resident), and **6,400 per 7.68 TB drive's wear at 3 DWPD** (12,700 with the compressed pool). A 128-core server is short of cores by a factor of 1.7 against its DRAM; a 256-core server is short of DRAM against its cores by 1.1–1.25; both are short of drives, which are consumed in proportion to density. The balanced server for this workload has about 200–230 cores per TiB of installed DRAM (900 GiB usable) and one 3 DWPD drive per 6,000–13,000 sandboxes.
- **The service level.** Counting *resident* sandboxes at a wake bound that can be met from storage (500 ms or 5 s) makes DRAM nearly irrelevant; counting at 50 ms makes the record's miss rate the floor; counting *active* sandboxes is the CPU bound alone.
- **The metric.** Density counts sandboxes. Where the count is CPU-bound on both sides, the kernelet's remaining advantages are per-sandbox memory (2.2× smaller warm than keep-warm, 1.05× smaller than DAX), wake cost (no VMM, vCPU thread or EPT to rebuild) and storage traffic (incremental, kernel-directed), which a density count does not see.

`K`'s floor (1–2 MiB) and value (5 MiB kernelet, 10 VM); the working sets of `P_proc` and `F_written` during a burst (the model's full values are used, and the true floor on `m_act` is the touched set); the kernelet's own `c_mech` (0–10 %) and the Linux-to-Asterinas kernel-path ratio inside `c_kernel`; the dirty set per idle cycle (24 MiB, taken equal to the hot set and assumed evicted and rewritten every cycle, an upper bound) and how much of the hot set is public; `T_act` = 60 s and the wake rate it implies; the miss rate of the wake record, which decides whether C15 meets 50 ms and whether the 500 ms floor of zero is reachable; the drive's queue tail at the utilizations used (M/D/1 figures, no measurement); the drive's rating (3 DWPD) and the incremental hibernation the 5 s row assumes; the drive count; and, as everywhere in `density/`, every kernelet mechanism, since nothing of the design has run.
