# C01: Shared image pages

**Status:** adopted, revised after review. **Depends on kernelets:** the *saving* does not (DAX-capable VM stacks and every container-class sandbox already read file pages from the host's page cache); the *mechanism cost* does: no EPT, no DAX window to size, no VMM. Labeled G with a kernelet advantage in cost. **Acts on:** `m_file(public)`, the public image content a sandbox has read.

## The problem, measured

A microVM that reads files keeps a private copy of every page it read, in its guest page cache, on top of the copy the host holds for the same image. On this host a 256 MiB Firecracker guest that read the Ubuntu toolchain directories once (205 MiB of files) went from 47 MiB to **245 MiB** of host RSS and stayed there (`../../benchmark/results/firecracker-raw.md`, `cache256`); after a snapshot restore and one work burst a guest held **187 MiB private**, of which 164 MiB was page cache (`burst256`). A resident Python runtime with a dozen common modules holds 23 MiB of cached file pages; a resident Node.js 22 runtime holds 52 MiB, most of its 118 MB binary (`py256`, `node256`). The guest never gives that memory back on its own: with the balloon's free-page reporting enabled the host recovered it only after the *guest* dropped its caches (RSS 245 → 76 MiB within 5 s), which an idle guest does not do, and forcing it means balloon inflation, which Firecracker's documentation calls CPU-intensive.

How much of what an agent reads is *public*, that is, content of the image every sandbox on the machine shares, is a property of the platform: an image with the toolchain and dependencies baked in makes most of `F` public; a sandbox that runs `pip install` or `npm install` after creation writes those files privately. The measurements bracket `F_public` between **23 MiB** (a runtime and its standard library) and **199 MiB** (a whole-tree sweep); the model's default is **200 MiB** public and **100 MiB** written, and the alternative, dependencies installed per sandbox, is 100 and 200.

## The mechanism: borrowing image grains

The kernelet's window is indexed by physical address and mapped by the host (Blueprint, Memory page, register D58), so a host frame can be handed to a kernelet without a copy by mapping it at `KW_PHYS + paddr`. The unit is the **grain**, not the page: the Blueprint's owner array has one entry per 2 MiB grain, `KW_PHYS` maps 2 MiB entries, and the metadata window is sparse per grain, so borrowing must be grain-granular.

- The host keeps every shared image in an **image arena**: the image's contents, stored uncompressed, in 2 MiB-aligned host segments that the host's page cache for image files is allocated from (the host's own file system serves the image through them). Arena grains carry an `Image(image_id)` owner-array state beside free, host and granted.
- The endovisor's **shared image** device serves a read-only file system (the `virtiofs` client the kernel proper has, over a FUSE-like backend) whose `read` reply is not bytes but the physical address of the image grain and the offset in it. One service call, `image_map(dev) -> (paddr_base, grains)`, at mount, maps the whole image read-only into the calling kernelet's window as 2 MiB entries, allocates and charges the eight metadata frames per borrowed grain that `KW_META` needs, and records the borrow in a per-kernelet **borrow table** on `Kernelet`, a new field and therefore a new step in the destroy drain list (`image_unmap` is the reverse). A 2 GiB image is 1,024 entries. `max_paddr()` in vOSTD becomes the machine's top, so the tree's bounds check accepts arena addresses; the metadata window stays sparse.
- Inside the kernelet, a borrowed frame is marked in its (kernelet-private) `MetaSlot`, and two rules in vOSTD, trusted code as everything about the kernelet's page tables is, keep it read-only and out of the allocator: `CursorMut::map` and `protect_next` refuse `PageFlags::W` on a borrowed frame, which also closes the tree's path that upgrades a private mapping to writable in place when the frame's reference count is 1 (`vm_mapping.rs`), and the last-reference drop of a borrowed frame returns nothing to the buddy allocator, since the tree's `Frame` drop otherwise calls `dealloc` and the arena grain would surface later as a writable anonymous page. Both are OSTD-level changes listed on the taxonomy page, not `cfg` lines in the kernel proper.
- The kernel proper's page cache needs one new commit path: the tree's `commit_on_internal` allocates a page and asks the backend to fill it; the shared-image backend instead installs the borrowed frame, through a new vOSTD constructor `Frame::from_borrowed(paddr)`, safe for the kernel proper to call. Private (`MAP_PRIVATE`) mappings of image files already work by the tree's own copy-on-write: `prepare_page` maps them read-only and `duplicate_frame` copies on the write fault. One thing to verify on the tree before counting shared libraries as public: under an overlay root, `overlayfs` returns the upper layer's page cache, which may copy a lower-only file up on `mmap` and lose the share.
- Images are immutable in place: the host never writes a frame that a kernelet may have borrowed, since a change under a tenant's ELF or `.pyc` parsing is a time-of-check race against every tenant. Updating an image means a new arena.

`virtiofs` DAX does the same for a VM by mapping host page cache into a guest-physical window through the EPT (LWN, "virtiofs: Add DAX support", 2020; a kata-dev message of May 2021 gives the example of a 300–350 MB `dnf install` costing nothing extra in the guest with DAX). Firecracker has no `virtiofs` (its issue #1180 is open and the port was never merged), and Kata ships DAX off by default (`virtio_fs_cache_size = 0`); QEMU and Cloud Hypervisor stacks can turn it on. The kernelet needs no EPT and no DAX window: the frame's physical address is its name.

## Gain

Per sandbox after a work burst, the private copy of public content goes from `F_public` to a residue of about **2 % of `F_public`**: the per-kernelet metadata frames for borrowed grains (64 B per 4 KiB page, 1.56 %, which cannot be shared because they hold each kernelet's own reference counts), the kernel-half page-table entries, and the kernelet's page-cache index nodes. With the default `F_public = 200 MiB`: **200 → 4 MiB**, so the warm sandbox of the model goes from 372 MiB to about **176 MiB** from this candidate alone, **2.1×**; with dependencies installed per sandbox (`F_public = 100`), 372 → 274 MiB, 1.35×. The earlier draft's 4.1× assumed 280 MiB public of 300 and no residue; that holds only for an image that already contains everything the agent reads.

The arena is one copy per image per server, shared by every sandbox using it; on Linux it would be droppable page cache, but the Asterinas host's page cache has no eviction on the tree (`kernel/core/src/vm/page_cache/mod.rs` says so), so on the design's host a borrowed grain is simply pinned by the host's own `Frame` reference count while any kernelet borrows it, and the pinned set is bounded by the sum of borrowed working sets over distinct images, not by "the image size" when tenants supply images. Two policy rules bound it: a per-kernelet `max_borrowed_grains`, and a charge, the first borrower's account or a `1/n` share, so that a tenant cannot pin an image for free against invariant I6; C03's idle eviction drops an idle kernelet's borrow table, and the wake refaults the mappings without a disk read, since the arena stays hot.

## Evidence

- Measured: 205 MiB read → 198 MiB of additional host RSS (`cache256`); 164 MiB retained as guest page cache after a burst in a 256 MiB guest (`burst256`); 23 MiB (Python) and 52 MiB (Node.js) of runtime file cache while idle (`py256`, `node256`).
- Published: `virtiofs` DAX removes the guest copy for shared directories; Kata's default configuration leaves it off; Firecracker lacks the device.
- Analytic: the gain is `0.98 × F_public`, whatever `F_public` is.

## Isolation

The shared frames are read-only content of one image, mapped read-only by the host; a tenant cannot write them, and a kernelet cannot map them writable while vOSTD's two rules hold, which are of the same trust as every other property of the kernelet's own page tables (Blueprint, Boundaries and trust). What remains is the residual every container-class sandbox has: a tenant that `mmap`s a borrowed library page can `clflush` it and time its own reload against other sandboxes' use of the same page (Flush+Reload); content inference is impossible, since the content is public. That is weaker than a microVM without DAX, which shares nothing; the Blueprint's threat model puts micro-architectural side channels out of scope, so the floor accepts it, but the effect is not "none": it is **container grade**, and it is the same class that made C09's content deduplication unacceptable, without C09's content leak. The platform can offer a per-sandbox opt-out, `share_image = false`, that copies every file page into granted frames, as Kata's caching modes do. A logic bug in vOSTD's write-refusal would be a cross-tenant *integrity* fault, a step above the same bug on a granted frame; it is the one place in the scheme where vOSTD's correctness protects other tenants rather than the host.

## Cost

- One service call per image mount, not per page; a `read` of a mapped page is a copy inside the kernelet with no crossing.
- Per borrowed grain: one 2 MiB window entry, eight metadata frames (32 KiB) charged to the borrower; ~4.5 MiB per sandbox at 280 MiB borrowed, ~3 MiB at 200.
- Per image per server: one uncompressed copy in the arena, pinned while borrowed.
- OSTD changes: two vOSTD rules, one constructor, one page-cache commit path, `max_paddr` semantics; a host-side arena allocator and borrow table.

## Changes to the Blueprint

Recorded here, not applied: an `Image` owner-array state and a per-kernelet borrow table with its drain-list step; `image_map` and `image_unmap` on the service table (23 functions); the shared-image device model in the endovisor with the arena; in vOSTD, the borrowed bit in `MetaSlot`, the write refusal in the cursor, the drop rule, `Frame::from_borrowed`, and `max_paddr` as the machine's top, all listed in the taxonomy; in the kernel proper, the borrowed-frame commit path under the feature; the Memory page's rule that borrowed frames are never granted, freed or zeroed by the kernelet's death; the endovisor policy's `max_borrowed_grains` and charge; the runtime's `share_image` option.
