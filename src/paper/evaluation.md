# Evaluation

**What must be measured, and how.** No measurement of Asterinas Kernelets itself exists, and the performance claim is a hypothesis until one does. The evaluation the design commits to has four parts, each answering a question the earlier sections leave open. *The cost of the boundary*: a crossing with the resolver and the stack check, a switch with the CR3 write and the window flush on same-kernelet and cross-kernelet switches, the kernel-mode fault path, an allocation through the owner array, and a virtio descriptor through the backend, each against the prototype's floors above and against a plain function call, a KVM exit and native Asterinas. *Isolation*: fault injection next to a real workload, a kernelet that exhausts its grant, one that spins with preemption disabled, and an adversarial create-and-destroy loop with leak assertions on frames, handles and channel rows, to test the drain list and the abandon primitive under concurrency. *Compatibility*: the Linux test suite and unmodified applications inside a kernelet, against the same kernel built as the host. *Density and lifecycle*: create, destroy and the memory floor per sandbox against Docker, gVisor and Firecracker on the same machine, and kernelet fork against a snapshot restore. The trusted base is measured the same way the prototype's was, by reachable function bytes from kernelet code, before and after the two build levers that remove most of the third-party code.
