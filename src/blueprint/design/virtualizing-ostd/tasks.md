# Tasks, scheduling, and CPUs

*Part of question 2. Virtualizes `task`, the sleeping half of `sync`, `cpu`, and the schedule handlers. Discharges invariants I4 (no retained reference), I5 (no closure crosses), I6 (charged CPU time) and the per-task half of I7 (termination).*

Every task of a kernelet is a host task: it has the host's `Task` object, the host's 512 KiB kernel stack (measured on the tree), the host's saved callee registers, and a place in the host's scheduler. What the kernelet has of it is a **name**, and what the kernelet's kernel has of it is the identical `Task` API over that name. The host scheduler decides which task runs and where; the kernelet decides what its tasks do.

## `Task` over a name

```rust
// OSTD (kernelet build), the virtualized `Task`. Same public API as the host build's, plus two builders.
pub struct Task {
    name: Cell<Option<TaskName>>,                     // the host's name for it, once `run` has spawned it
    data: Box<dyn Any + Send + Sync>,                 // the kernel's, as today
    local_data: ForceSync<Box<dyn Any + Send>>,       // the kernel's, as today
    schedule_info: TaskScheduleInfo,
    affinity: CpuSet, priority: u32,                  // hints passed to the host at spawn
}
pub struct CurrentTask(NonNull<Task>);                // as today

/// The kernelet's counterpart of the host's `CURRENT_TASK_PTR`: one raw pointer per task
/// index, holding a strong `Arc<Task>` from `run` until `task_exit`, read lock-free.
static RUNNING: [AtomicPtr<Task>; MAX_TASKS];
/// Bodies waiting to run, by entry index; indices start at 2, since 0 and 1 are the
/// host's. The host sees only the index (invariant I5).
static BODIES: SpinLock<Slab<Box<dyn FnOnce() + Send>>>;
```

- `TaskOptions::build` returns the `Task` by value, as on the tree, and makes no crossing. `Task::run(self: &Arc<Self>)` is where the host learns of the task: it stores the body in `BODIES`, calls `task_spawn(entry, 0, &affinity, priority, SPAWN_SUSPENDED)`, records the returned name, publishes the `Arc` into `RUNNING[index]`, and only then calls `task_unpark(name)`. Registering before unparking is what keeps `Task::current` on the new task from finding nothing if the host runs it on another CPU at once. `TaskOptions::spawn` is `build` then `run`: two crossings.
- `Task::current` is one GS-relative load of the CPU slot's `task` and one load of `RUNNING[index]`, no lock; `CurrentTask` is the same non-`Send` handle as today. The `Arc` in `RUNNING` is the one strong reference the tree keeps in `CURRENT_TASK_PTR` and the run queue; a kernelet-side `Task` is never freed while its host task runs. `task_exit` on the kernelet side drops it after the host has switched away, which is why `run_task` ends with a service call rather than a return.
- A built task that is never run is dropped by the kernel proper as today, and `impl Drop for Task` calls `task_destroy(name)` if it was spawned suspended and never unparked, so that no host task or stack leaks.
- The host's trampoline, on the new task, calls `run_task(entry, arg)`, which takes the body out of `BODIES`, calls the injected post-schedule handler, runs the body, activates the kernelet's kernel page table ([Memory](memory.md)), and ends with `task_exit`.
- `Task::yield_now` is `task_yield`. `Task::need_yield` reads `NEED_RESCHED` from the task record's mirror.
- `disable_preempt` increments the `preempt_count` in the record of the task named in the CPU slot, which is the running task, instead of a per-CPU count, and the guard decrements it; `might_preempt` at the kernelet's preemption points reads the mirror and yields. A per-task count is equivalent to a per-CPU count here because the host never moves a task whose count is nonzero (below). The count lives on a cache line the host tick reads from another CPU, so every spin-lock acquire and release now touches a shared line rather than a GS-local one; that is a cost the Evaluation chapter measures.
- Two builders are added to `TaskOptions` in both builds, `cpu_affinity(CpuSet)` and `priority(u32)`, with setters `Task::set_cpu_affinity` and `set_priority`. In the host build they set the schedule hint the injected scheduler already reads; in the kernelet build they are the values passed to `task_spawn` and to `task_set_vcpus` and `task_set_prio`. The kernel proper's `ThreadOptions::build`, its `sched_setaffinity` path and its scheduler classes get one `cfg` line each to call them, listed in the [taxonomy](index.md)'s inventory; without those lines the kernel's per-CPU daemons, `softirqd`, the work-queue workers and the per-CPU idle threads (checked on the tree: `kernel/core/src/thread`), would land on arbitrary virtual CPUs and their per-CPU bookkeeping would break.
- `halt_cpu`, which only the kernel proper's idle loops call (checked on the tree: `kernel/core/src/init.rs`), parks the calling task. An idle task is one the kernel proper spawned with `SchedPolicy::Idle`, which the `cfg` line in `ThreadOptions::build` passes down as `SPAWN_IDLE`; the host runs it only when its virtual CPU has no other runnable task of the kernelet, and wakes it *edge-triggered*, once, when the virtual CPU's last other runnable task parks or exits. The idle loops therefore run when the kernelet goes idle on that CPU, re-check their conditions, and park again, which is what `hlt` gives them today, and a fully idle kernelet consumes nothing. As on the host kernel, the boot CPU's idle loop is where init's exit is noticed, so a thread that never yields on virtual CPU 0 delays that notice, exactly as it would on hardware.

## Waiting and waking

`WaitQueue`, `Waiter`, `Waker`, `Mutex` and `RwMutex` keep their code; only the two primitives beneath them change. A `Waker` keeps holding the sleeper's `Arc<Task>`, as on the tree, since it never crosses the boundary and `Waiter::task()` returns a reference to it (checked on the tree: the kernel's pause paths use it); `Waker::wake_up` derives the name from the `Arc` and calls `task_unpark(name)`, and `Waiter::wait` calls `task_park`. The park token of the service half is what makes the identical `wait_until` correct: OSTD's `wait_until` enqueues the waker and then re-checks the condition before parking, and an unpark that arrives between the check and the park is remembered as the token and consumed by the park, the rule `park_current(has_unparked)` enforces on the tree. A park ended by `kill` never returns to kernelet code: the service epilogue terminates the task there.

`RwArc`, the spin locks and the RCU read side are identical. The RCU write side is virtualized without a crossing. OSTD's grace-period monitor keeps a mask of CPUs that have passed a quiescent state since the period began, advances it in `switch_to_task`, and restarts with an empty mask (checked on the tree: `ostd/src/sync/rcu/monitor.rs`, `ostd/src/task/processor.rs`). In the kernelet build the mask is over virtual CPUs and is advanced at the kernelet's own switch points: a park, a yield, a return from `user_run`, and the top of the worker's job loop. That would never complete while any virtual CPU is idle, since an idle CPU runs no switch point; so each virtual CPU also has an **extended quiescent state** bit, set when its last task parks, when its worker enters `job_wait`, and when its idle task parks, and cleared when a task resumes on it at a kernelet switch point; a period's restart treats a virtual CPU in that state as already quiescent, which is the rule tickless kernels use. It is sound because a task inside an RCU read section holds preemption disabled, so the host does not move it off its virtual CPU until the section ends, and a virtual CPU in the extended state has no task in a read section. **[unverified]** (register A9): the soundness argument under every path by which a task can leave a virtual CPU. Pending `RcuDrop` callbacks run on the worker after the tick that completes the period, instead of at the next switch, which delays reclamation by up to one tick.

## The scheduler

There is one scheduler on the machine, the host's, and a kernelet is a **group** in it with a weight and an optional quota, the `CpuBudget` of its configuration. Every task of the kernelet is a member; the host picks among a group's tasks with its own policy and honors two hints from the kernelet, a per-task priority and a per-task virtual-CPU set. The kernel proper's own scheduler, the class scheduler it injects with `inject_scheduler`, is inert inside a kernelet: `inject_scheduler` stores the reference and nothing calls it, `enable_preemption_on_cpu` does nothing, and the `Scheduler` and `LocalRunQueue` traits, `EnqueueFlags` and `UpdateFlags` are identical types nothing dispatches through. The reason is the entry rule: the host must not call into the kernelet image to ask which task to run next, because that would enter kernelet code from the scheduler's own path, with run-queue locks held, from a task that is not the kernelet's. What the tenant loses is stated below.

**Kernel-mode preemption.** OSTD today preempts only at voluntary points: the tick sets a flag that `might_preempt` consumes at the return to ring 3 and at a few task-context points, and nothing switches on an interrupt's return to ring 0 (checked on the tree: `ostd/src/task/scheduler/mod.rs`). A kernelet spinning in kernel mode would therefore hold its host CPU. The host build adds one mechanism, `preempt_switch`: on an interrupt's return to ring 0, if the return address lies in `KW_TEXT` and the current task's host-private `service_depth` is zero, the host reads the task record's `preempt_count` and the CPU's need-preempt flag and, if the count is zero and the flag set, switches tasks there; if the task's kernelet is dying, it terminates the task there instead ([Faults, termination, and reclamation](../faults-and-reclamation.md)). `preempt_switch` is not `switch_to_task`: it is entered with interrupts disabled, skips the `might_sleep` assertion and both schedule handlers (the tree's `switch_to_task` asserts it may sleep and calls the handlers, which would panic here; checked), saves the user state below, writes the CPU slot, and returns into `after_switching_to` on the next task, which re-enables interrupts before the trap's `iretq`. **[unverified]** (register A8): that the host can switch tasks from the interrupt-return path with every invariant of OSTD's trap and switch code intact. If `preempt_count` is nonzero the host counts the tick against `policy.preempt_off_ticks` and, at the budget, kills the kernelet with `PreemptOffTooLong`. Host code, including a service call in progress, is never preempted by this path, so the host's own lock discipline is unchanged. *Estimated* cost, on every interrupt return to ring 0 machine-wide: two compares for the address range, a load of the current task pointer and its depth, a load of the record's count and one of the flag, about five loads.

**What the host saves on an involuntary switch.** The kernel proper saves a thread's user FS base, GS base and FPU state in its pre-schedule handler before a voluntary switch and reloads them before the next user run (checked on the tree: `kernel/core/src/process/posix_thread/thread_local.rs`, `before_schedule`); OSTD's own context switch saves only the callee registers (`ostd/src/arch/x86/task/switch.S`). A kernel-mode preemption is a switch the kernel proper does not see, so `preempt_switch` saves the FS and GS bases and an XSAVE area into the task's host-private `SavedUserState`, and the host restores them when it switches back. The other place user state is live in the CPU is inside `user_run`, at depth one; `user_run` therefore never switches tasks itself: an interrupt that arrives in user mode is handled and `user_run` returns `2`, and the kernelet's `might_preempt` yields at depth zero, after the kernel proper's own pre handler has saved the state ([User mode](user-mode.md)). Cost: an XSAVE and an XRSTOR per involuntary switch of a kernelet task, which today's kernel avoids by saving lazily at voluntary points; *estimated* at a few hundred cycles per switch, to be measured.

**The schedule handlers.** `inject_pre_schedule_handler` and `inject_post_schedule_handler` are accepted, and OSTD (kernelet build) calls the pre handler before each of its own voluntary switch points (`task_park`, `task_yield`, `task_exit`) and the post handler after each returns and at a task's first entry. The pre handler takes a `DisabledLocalIrqGuard`, a preemption guard in the kernelet build, and the switch on the tree happens under it; here the guard is dropped before the crossing, since a sleeping service call is refused under a nonzero count, and the gap is harmless: a preemption in it is an involuntary switch, whose state the host saves and restores. The host's own handlers see nothing of kernelet tasks. The kernel proper's post handler activates the thread's `VmSpace` (checked on the tree: `kernel/core/src/thread/mod.rs`); inside a kernelet that activation is `pt_activate`, keyed per task so that it stays correct across involuntary switches, which restore the same root ([Memory](memory.md)); `VmSpace::cpus`, the tree's record of where a space is active, is advisory in the kernelet build, since the host's own active set is what `tlb_shootdown` uses.

**Charging.** The scheduler attributes a task's CPU time to its kernelet's group, which is invariant I6 for CPU time; the group's quota, if any, is enforced there. Time spent in a service call, in a hook, or in the host's fault handler on the kernelet's behalf is on the kernelet's task and counts. A device thread the endovisor adopts into the group counts too.

## Virtual CPUs and per-CPU state

A kernelet's configuration names a set of host CPUs; its virtual CPU `i` is the `i`-th of them. `num_cpus`, `all_cpus` and `CpuId::current` are virtualized without a crossing from `BootArgs` and the CPU slot's `vcpu`. The kernelet's tasks are confined to that set by their affinity, so a task always runs on a host CPU that has a virtual CPU index in this kernelet.

`cpu_local!` and `cpu_local_cell!` are virtualized without a crossing. The kernelet image's `.cpu_local` section is replicated once per virtual CPU after the writable segment ([Builds and images](../builds-and-images.md)), and OSTD (kernelet build) addresses a static's replica as `replica_base + vcpu × replica_bytes + (static_addr − cpu_local_start)`, with `vcpu` read from the CPU slot under a preemption guard, which is the guard `cpu_local!` already requires. On the tree the address is formed from the GS base (`ostd/src/cpu/local/static_cpu_local.rs`); the GS base is the host's, so the kernelet build forms it from the slot instead, two loads more per access. `CpuLocalCell`'s single-instruction operations are `gs:`-relative read-modify-writes on the tree precisely so that their callers need no guard (checked: `ostd/src/arch/x86/cpu/local.rs`; the softirq pending mask and the tree's own `CURRENT_TASK_PTR` rely on it). In the kernelet build each such operation raises the task record's `preempt_count` around its load-compute-store, so that a kernel-mode preemption cannot move the task between forming the address and using it; that is two extra stores on the shared line per operation. It is sound because nothing in a kernelet runs in interrupt context, so there is no handler to race with. The frame allocator's and the heap allocator's per-CPU caches, the softirq component's per-CPU pending masks, and the kernel's per-CPU statistics all use these, and all keep their code.

A task may hold `preempt_count` nonzero and touch per-CPU state knowing it will not be moved, and the host guarantees that by the preemption rule above. The one way a kernelet task changes host CPU is at a point where its count is zero.

## What a tenant sees

- `nproc` and `/proc/cpuinfo` report the kernelet's virtual CPUs.
- `nice`, `sched_setscheduler` and the real-time policies have no effect beyond the priority hint the `cfg` line forwards: the host schedules every thread of a kernelet within the kernelet's budget by its own policy. `sched_setaffinity` to a subset of the kernelet's virtual CPUs works, through `task_set_vcpus`; beyond the set it fails as it does for CPUs a process is not allowed. This is the largest compatibility gap on this page, and it is a consequence of the entry rule, not of a missing mechanism.
- `/proc/loadavg`, the run-queue fields of `/proc/stat`, `sysinfo(2)`'s load figures, `sched_getscheduler` and `getpriority` are computed by the inert class scheduler (checked on the tree: `kernel/core/src/sched/stats`), so they report zero load and the policy values the tenant set rather than what the host does.
- A thread that spins in kernel mode is preempted by the host, which it is not on the host kernel today.
- Nothing else: process creation, threads, waiting, signals and timing behave as on the host kernel.

## Costs

- Per task: a host task, a 512 KiB stack with four guard pages, a slot in `RUNNING`, and a 64-byte record; a spawn is two crossings, one to create and one to run.
- Per park and per wake: one crossing each, against a scheduler call today.
- Per `cpu_local!` access: two loads more than a GS-relative access; per `CpuLocalCell` operation, two stores more as well.
- Per spin-lock acquire and release: the preemption count on a shared cache line instead of a GS-local one.
- Per involuntary switch of a kernelet task: an XSAVE and an XRSTOR (*estimated*, a few hundred cycles) and a CR3 restore.
- Per interrupt return to ring 0, machine-wide: about five loads and two compares (*estimated*).
- Per virtual CPU: one worker task and one idle task's stack.

## What this page decides

- **The kernel proper's scheduler is inert inside a kernelet** (register D15). The alternative is to consult it as a second-level policy from the host's run queue, entering the kernelet image from the scheduler's path with locks held, on a task that may not be the kernelet's; that breaks the entry rule invariant I7 rests on. The compatibility cost is stated above, and the priority and affinity hints, passed through two builders added to `TaskOptions` (register D31), recover most of it.
- **Kernel-mode preemption exists only for kernelet text** (register D16), through a switch path of its own, `preempt_switch`, since the tree's `switch_to_task` cannot be entered from an interrupt.
- **The host saves user TLS and FPU state on involuntary switches** (register D17), and `user_run` never switches, so that the two places where user state is live in the CPU are both covered.
- **Per-virtual-CPU RCU with an extended quiescent state for idle CPUs** (register D32). The alternative, tracking quiescence per task, would make a grace period wait for every task of the kernelet, including ones parked for the life of the sandbox.
