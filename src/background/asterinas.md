# Asterinas in ten facts

Ten facts about the tree, each of which a later section relies on.

**The framekernel.** All `unsafe` code lives in OSTD (about 45,600 lines, of which about 6,000 are proven in Verus as `vostd`); the roughly 183,000 lines above it are `#![deny(unsafe_code)]` and contain no `unsafe` block. OSTD exposes safe abstractions for the sensitive resources: page tables (`VmSpace` and its cursor), CPU context (`UserMode`, `UserContext`), tasks (`Task`), interrupts (`IrqLine`), device memory (`IoMem`, `IoPort`, `DmaStream`, `DmaCoherent`), and untyped memory (`Frame<()>`, `Segment<()>`, `VmReader`, `VmWriter`).

**The kernel half of the address space.** On x86-64 with four-level paging, the top-level page table has 512 entries of 512 GiB each. Entries 0–255 are the user half, owned by a `VmSpace`. Entries 256–511 are the kernel half: OSTD allocates a level-3 table for every one of them at boot and *shares* those tables into every `VmSpace` by copying the 256 top-level entries when a user page table is created (`ostd/src/mm/page_table/mod.rs`, `create_user_page_table`, which takes a `'static` parent and does not reference-count the shared nodes). The linear map of all physical memory occupies entries 256–383, the vmalloc area 384–447, the frame-metadata array 448–449, and the image 511; entries 450–510 have level-3 tables and nothing under them. Kernel mappings carry the Global bit, so a CR3 write does not flush them; kernel stacks do not, and are flushed. The tree does not use PCIDs.

**Kernel tasks.** A `Task` owns a 512 KiB kernel stack and a saved register context, and carries two opaque slots the kernel fills. The kernel's post-schedule handler, which OSTD calls after every switch, activates the incoming task's `VmSpace` if it has one and otherwise leaves CR3 alone, so a task with no `VmSpace` (a kernel thread, the idle loop) runs on whatever page table its predecessor left; OSTD's own `KERNEL_PAGE_TABLE` is activated at boot and, in OSTD's words, is unlikely to be activated again.

**The image.** OSDK drives the build and owns the linker script (`osdk/src/base_crate/x86_64.ld.template`), which places `.data`, `.bss` and a per-CPU-replicated `.cpu_local` section and uses `AT()` to separate a section's virtual address from where the boot loader puts its bytes. Anything a link-time check must see is in the artifact OSDK produces.

**Lock guardians.** `SpinLock<T, G>` takes a guardian `G` that says what must hold while the lock is held: `PreemptDisabled` bumps a per-CPU count, `LocalIrqDisabled` clears the interrupt flag, `WriteIrqDisabled` does so on the write side of a reader-writer lock. The sleepable `Mutex` and `RwMutex` are an atomic flag plus a `WaitQueue` whose waiter list is an interrupt-disabled spin lock; a park holds an `Arc<Task>` for the sleeper.

**The syscall context.** `kernel/core/src/context.rs` defines `Context<'a>`, built once per user task and passed to every syscall handler; 201 of the kernel's 1,051 files take it.

**Preemption.** The tree has no kernel preemption: the tick sets a flag that is consumed only at voluntary points (the return to ring 3, the end of a spawn, the idle path), never on an interrupt return. The thread-state module's own comment says kernel preemption needs the per-thread register state moved out of the kernel's `ThreadLocal`.

**The oops mechanism.** Every user task's body runs under a `catch_unwind`; the default profiles unwind. A panic that cannot unwind (inside a destructor during unwinding, or beneath the assembly trap stubs, which carry no unwind information) aborts the machine. The oops budget is one global counter. OSTD has no interrupt-stack-table entry and no double-fault handler: a kernel stack overflow into its guard page is a double fault with no stack to take it on, which is a triple fault and a reset.

**Allocators as hooks.** The kernel binds its heap and frame allocators into OSTD with three attribute macros; both hook traits are safe traits, and the slab allocator in `osdk/deps` is itself `#![deny(unsafe_code)]`. OSTD's slab addresses every slot through the linear map: `Slab` derives slot addresses from the frame's physical address, `HeapSlot::paddr()` subtracts the linear-map base, and the free list is intrusive, dereferencing the slot being freed. The build's release profiles link with LTO (`lto = "thin"` and `lto = true`), so the linker sees merged objects rather than per-crate archives.

**Virtio.** The kernel's virtio component (`kernel/core/comps/virtio`, 8,339 lines; block, network and console devices on top) is safe Rust written against `IoMem`, `DmaStream` and `IrqLine`, with two transports: MMIO, where a device is a register file at offsets in one `IoMem`, and PCI, which additionally parses configuration space through the PCI component and allocates MSI-X vectors. A virtio device's queues (a descriptor table, an available ring and a used ring) live in memory the driver owns and tells the device about by writing their addresses to registers.
