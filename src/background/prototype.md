# An earlier prototype: a software hypervisor with API virtualization

Alternative B was built and booted: a framekernel *virtualization layer* between OSTD and one or more *guest kernels*, on the same hardware privilege level, with no VT-x and no nested paging, measured on a dual Xeon Gold 6348. Its shape:

- **API virtualization instead of hardware emulation.** A guest is an unmodified framekernel OS service. The virtualization layer re-implements, with virtualized semantics, only those OSTD APIs that can change global state (interrupt control, device I/O, task creation); purely local library code (`xarray` is its example) is reused untouched. A guest built against OSTD runs as the root kernel; the same source built against the virtualization layer runs as a guest.
- **Per-instance kernel page tables for writable sections.** To run many instances of one code image, the read-only `.text` is shared and each instance gets a private physical copy of `.data` and `.bss`, mapped at the same virtual addresses by an instance-level kernel page table, with the virtualization layer and OSTD mapped identically into every instance. (Designed as future work; the prototype ran one instance.)
- **vCPUs and two-level group scheduling.** Each guest's tasks form a task group under OSTD's injected scheduler with a weight; a per-vCPU *interrupt handler task* in the guest's group is woken at top priority when events are pending, sleeps when the guest "disables interrupts", and a lock holder that disables interrupts is boosted to the handler's priority until it releases. No IPI virtualization: cross-vCPU synchronization is flags and wakeups.
- **Paravirtual I/O with no traps.** The guest's virtio drivers run unmodified against an `IoMem` that maps to no hardware; each register access is a function call into a backend device model, which validates the request and forwards it to the root kernel's real driver; completions arrive as software interrupts. A passthrough mode hands a real `IoMem`, `DmaStream` and interrupt line to a guest with the IOMMU restricted to that guest's frames.
- **Remote references and a zero-copy vsock.** Cross-instance data lives on a shared heap behind `RRef<T>`, where `T` must be *exchangeable* (a closed set: `Copy` primitives, `RRef` itself, and composites of those; no references or pointers). A global table records each object's owner, borrowers and type. Transfer is a metadata update, not a copy. On that, `AF_VSOCK` semantics: connection control by synchronous function call, data by `RRef` ownership transfer, per-vCPU lock-free receive queues, batched delivery.
- **Measured, on the booted prototype:** a call into the virtualization layer costs 35 cycles against 34 for a plain function call and 5,155 for a VM exit and entry; an `RRef` create, send and destroy cost 104, 177 and 94 cycles; a stack-size check and a stack switch cost 39 and 100; a cold page fault costs 10,345 cycles in a guest against 9,791 in Asterinas itself and 33,307 in a nested Linux VM; the vsock reaches 67.68 Gbit/s on a single connection at 64 KiB payloads and 124.67 Gbit/s over four connections with four queues on four cores, with a 9.4 µs average round trip against 36.9 µs for virtio-vsock and about 4.3 µs for a native pipe.

What it got right, and this design keeps: API virtualization, which is the same idea as Alternative A's facade taken to its conclusion, zero source change; per-instance writable sections by page table, which is the cheap answer to the state problem Alternative A paid so much for; virtio over function calls, which reuses the kernel's drivers and gives the host a device surface with a public specification; ownership transfer under an exchangeable-type rule as the communication primitive; the interrupt-handler task in the guest's own group; the stack check at the boundary; and real numbers. Where it is weak, read critically:

1. **One instance ran.** The per-instance page-table mechanism, which is what makes the design multi-tenant, is a plan; global-state conflicts between instances of one image are named as future work.
2. **Its load-time checks cannot do what they say.** It loads guests as separately compiled relocatable objects and checks at load time that the object "contains no `unsafe` code" and was built with the same compiler and flags. Absence of `unsafe` is not a property of an object file; it is a property of a build, and can only be attested by whoever ran the build. Dynamic loading of untrusted kernel code is therefore not adopted here.
3. **Fault containment is described only for `RRef`.** What happens to a guest that panics inside a critical section, exhausts memory, or spins with preemption disabled, and how its tasks, stacks and heap are reclaimed, is not designed. This is the half of the problem Alternative A spent most of its effort on.
4. **The guest chooses which of its tasks runs.** Two-level scheduling as described reintroduces the semantic gap it set out to remove (a guest can pick a lock holder to deschedule); Alternative A's single hierarchical scheduler subsumes the task-group idea without it.
5. **"Zero copy" is kernel-to-kernel.** Application bytes are copied into the `RRef` on send and out of it on receive; two copies remain against a pipe's two. The win over virtio-vsock is real and is the removal of the third copy, the virtqueue and the exits.
6. **The virtualization layer's TCB is not measured**, and the root kernel's drivers, which parse device input, sit inside it.
