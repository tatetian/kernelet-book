# Introduction

This chapter fixes the vocabulary and the claims. It says what a kernelet, a sandbox, the host kernel and the endovisor are, restates the requirements the design answers, and states the design in five ideas. Everything later in the book elaborates one of those five.

## What a kernelet is, and what the host is {#what-a-kernelet-is}

A **kernelet** is one instance of the Asterinas kernel compiled against an OSTD-shaped facade, serving the user-space processes of exactly one tenant, running in ring 0, in the same image as every other kernelet. A kernelet together with the processes it serves is that tenant's **sandbox**, in the sense in which a virtual machine or a container is one. The **host kernel** is the full Linux-compatible Asterinas kernel that boots the machine, runs init and the host user space; it is the same kernel source built against OSTD itself. Inside the host kernel, the **endovisor** is the component that creates, schedules, destroys and mediates kernelets and implements the facade they are compiled against; where a hypervisor sits beneath its guests in hardware, the endovisor sits inside the host kernel and beside the kernelets, and its boundary is the crate graph, with per-kernelet page tables as a backstop, not a second layer of address translation. Sandboxes are created and configured from host user space by a **kernelet runtime**, in the way a container runtime creates containers. Every tenant must trust the host kernel; the parts of it that a kernelet's execution actually enters, the endovisor, OSTD, the drivers and the allocators, are the trusted computing base this book measures ([§3.5](../architecture/tcb.md)). A tenant is assumed to be hostile: it runs arbitrary native code in ring 3 and, through the syscalls it makes, drives arbitrary paths in its kernelet, which is safe Rust but which the tenant is trying to turn against its neighbors. Throughout this book "the host" means the host kernel, so host tasks, host locks and the host heap are the host kernel's; where the endovisor specifically is meant, it is named.

The requirements this design answers, restated from the problem it was set: no shared mutable state between kernelets by default (H1); no ambient authority (H2); mechanically checkable enforcement (H3); fault containment (H4); bounded resources, including denial of service, which is in scope (H5); complete reclamation of a destroyed kernelet (H6); the Linux ABI inside a kernelet (H7); typed crossings (H8); a small, auditable shared core (H9); no hypervisor, no nested scheduling (S10); enumerable nondeterminism (S11); fast create and destroy with a low memory floor (S12); a non-intrusive change to the tree (S13). Microarchitectural side channels are out of scope.
