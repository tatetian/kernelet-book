# The stack check at the boundary

A kernelet's kernel stack is host-owned and 512 KiB, but the kernelet chooses how much of it to use before calling the host: a deep recursion in safe kernelet code followed by a service call would overflow the guard page *inside host code*, which is a host fault and today a machine halt. Alternative B paid 39 cycles per call for a stack-size check and 100 for a switch to a dedicated stack. This design takes the check and not the switch: the service wrapper compares the stack pointer against the task's stack base plus a reserve (64 KiB, the deepest host path plus margin, to be measured) and, below it, terminates the calling thread with an oops instead of entering the host. A stack overflow *in kernelet code* hits the guard page in kernel mode, which today is a double fault with no stack and therefore a reset; OSTD change (17) gives the double fault an interrupt-stack-table stack and a handler that, when a kernelet task is current *and the task is at a quiescent point* (no host lock held, not in interrupt context), marks the kernelet dying and rewrites the exception frame to land in the landing function of [§4.7.1](../faults/tiers.md) on the task's own stack, near its top where the entry frame is, so that returning from the exception discards the overflowed frames. It cannot call the scheduler, which asserts that it is entered with interrupts enabled. An overflow while a host lock is held, inside the cursor or a user-memory copy, or in interrupt context, is a machine halt (T3 of [§4.7.1](../faults/tiers.md)), and [§7.1](../../limitations/losses.md) lists it. The check at the boundary is therefore also made at cursor creation, which is the one host-guarded path kernelet code enters without a wrapper.
