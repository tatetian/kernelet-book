# Two guardians, and a kernelet's "interrupts"

Kernelet locks and host locks are different types, and only host locks count toward the quiescence predicate. The kernelet guardian disables preemption, has its own guard type, and its spin loop polls the kernelet's dying flag; [OSTD's three guardians](../../background/asterinas.md), the host's sleepable locks and the page-table cursor bump [`HOST_GUARD_DEPTH`](../memory/arena.md). The RCU read guard and `disable_preempt()` count toward neither. The point is in [§4.7.1](../faults/tiers.md): a kernelet-held lock never delays killing that kernelet, because whoever waits on it is one of the kernelet's own tasks; a host-held lock always does, because abandoning a stack that holds one leaves the structure inconsistent for everyone.

Alternative B gave each guest a *virtual* interrupt flag: "disable interrupts" parks the guest's interrupt-handler task and boosts the lock holder. This design does something simpler, because in this design no kernelet code ever runs in interrupt context: every deferred event runs on the kernelet's worker in thread context ([§4.4.6](worker.md)), so the only reason the kernel disables interrupts around a lock, that a handler on the same CPU might take it, no longer exists. The facade therefore defines `PreemptDisabled`, `LocalIrqDisabled` and `WriteIrqDisabled` as **the kernelet guardian under three names**, and `disable_local()` returns a preemption guard. The kernel's 34 interrupt-disabling sites (lines matching the guardian names or `disable_local`, imports excluded) compile unchanged and mean "no preemption"; about half are in code that becomes host code anyway, and the two that pass the guard to an OSTD API demanding a real interrupt-disabled guard are in the thread-state protocol, which moves to the host. The property "kernelet code never runs with interrupts disabled" is then true by construction.
