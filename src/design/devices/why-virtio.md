# Why virtio, and why over function calls

One NIC, one disk, N tenants. Alternative A moved every driver into the host and invented typed request kinds for block, network, file, console and entropy for kernelets to use; and its device surface was new code with no specification behind it. Alternative B kept the guest's drivers and put a *virtio backend* behind them. This design takes Alternative B's split, and states why it is the better one:

- **Virtio is a public specification.** Its register file, feature negotiation, queue layout and per-device request formats are documented and fuzzed; every microVM's attack surface is exactly this set of backends, and the world knows how to review them.
- **The kernel already has the front-ends.** `kernel/core/comps/virtio` and the block, network and console devices on top of it are safe Rust over `IoMem`, `DmaStream` and `IrqLine`, all three of which the facade virtualizes ([§4.2.3](../facade/item-kinds.md)). Kernelets see **virtio-mmio** devices: the MMIO transport (one register file in one `IoMem`) runs in the kernelet unchanged; the PCI transport, which parses configuration space and allocates interrupt vectors, is host code. The facade's `IoMem` implements the same traits the front-ends use (`VmIo`, `VmIoOnce`, `HasPaddr`); its `IrqLine::on_active` takes the same callback type, and the trap frame that callback receives is a value the front-ends do not read (to be confirmed, [§7.2](../../limitations/todos.md) item 5).
- **No trap is needed to intercept a register.** A virtio device's registers are accessed through `IoMem::read_once`/`write_once` at an offset. The facade's `IoMem` is a struct holding a `Handle<VirtioDev>` and a register offset base; its `write_once` is a function call into the host, which matches the offset against the device's register map and updates a Rust struct. The booted prototype measured that call at 35 cycles, where a VM exit costs 5,155. There is no MMIO, no `#PF`-based emulation, no instruction decoding.
