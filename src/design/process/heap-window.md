# Putting the arena in the heap window

Alternative A's arena was reached through the linear map, like every other frame. Here the arena's grains are mapped at [`W_HEAP + offset`](two-windows.md) in the kernelet's level-3 table and the arena hands out heap-window addresses. A `Box<T>` in a kernelet holds a pointer that **resolves only on that kernelet's page tables**.

OSTD's heap does not support that as it stands: its `Slab` computes slot addresses from the frame's physical address through the linear map, its `HeapSlot::paddr()` subtracts the linear-map base, its large slots are whole `Segment`s taken from the frame allocator and rebuilt from the physical address on free, and its free list is intrusive (it dereferences the slot being freed). So OSTD change (16) of [§5.1](../../implementation/ostd-changes.md) makes the slab and the large-slot path generic over an address translation: the host heap uses the linear map as today, and a kernelet's arena uses its window, so that `HeapSlot::paddr()` on a window address consults the arena's grain table, and a large slot in the arena is carved from a grain's window range by the arena's own page allocator and never rebuilt as a `Segment` (the 1 MiB cap on infallible allocations of [§4.3.3](../memory/bands.md) is what keeps every large slot inside one 2 MiB grain). The free path then has a property Alternative A paid an owner-array read per free to get: **a window address belongs to the arena of the kernelet the current task serves**, because no other kernelet's window is mapped, so the dispatcher's `dealloc` routes on the address and on the task's kernelet (the `CURRENT_KERNELET` word of [§4.3.1](../memory/arena.md), not the heap word, which a host scope ([§4.2.4](../facade/services.md)) has cleared) and never looks anything up. A window-address free from a host task or in interrupt context is a bug the dispatcher asserts on, since dereferencing the slot would fault anyway. The linear-map alias of a grain's frames still exists (OSTD needs it to zero and poison frames at release), but no kernelet object is ever addressed through it, and check 4 of [§5.2](../../implementation/checks.md) says so.

What the window buys, stated with its limits:

- **A fault instead of a silent read for the bug class hardest to keep out by review.** The rule that the host retains no pointer into a kernelet's memory was enforced in Alternative A by a type bound and a poison pattern, and review of it found two host-internal holders (the per-CPU active address space and the cursor's deferred-free queue) that the bound could not see. Under the windows and the switch policy, a host task *in thread context* that dereferences a retained pointer into a kernelet's heap or data takes a page fault, because the host's page table maps nothing there. The limits: host code running *on a kernelet's task* (a service call, or an interrupt handler that interrupted that task) does map that kernelet's window, so a host bug that dereferences A's pointer while serving A reads A, and a host bug that dereferences A's pointer while serving B reads *B's own bytes* at that address. The windows separate host-in-thread-context from kernelets, and kernelet from kernelet; they do not separate "host acting for A" from "host acting for B", and the type bound stays for that.
- **Snapshot and fork at the address level.** A kernelet's two windows are self-consistent under copy, because every pointer in them is a window address that means the same thing in the copy. Alternative A rejected snapshot because a kernelet with parked threads has live kernel stacks; that objection stands, and a kernelet all of whose threads are in user mode or at the syscall boundary, with no I/O and no message in flight, can be forked by copying two windows and the host objects that name it. That is milestone 3 ([§5.3](../../implementation/plan.md)) and [§7.2](../../limitations/todos.md) item 15 says what it still lacks.
- **Not a defense against the host's own `unsafe` being wrong**, nor against a forged address (no kernelet can forge one; safe Rust cannot conjure a pointer and the other window is not mapped in any case), nor a replacement for the owner tag on frames ([§4.3.2](../memory/frames.md)): user frames, page-cache frames and page-table nodes are addressed through the linear map by OSTD, and the owner tag is what stops a kernelet handing the host a frame it does not own. And one kernelet-held pointer lives outside the windows on purpose: an `RRef` ([§4.6.2](../channels/rref.md)), whose buffer is a host object in the shared kernel half, and whose safety rests on its own argument.
