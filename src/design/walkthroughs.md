# Three paths, end to end

## `read(2)` on a file whose page is not cached {#read}

A thread in kernelet 7 calls `read(fd, buf, 4096)`. The syscall dispatcher, the fd table, the inode and the page cache are all kernelet code operating on kernelet state in the data and heap windows: zero crossings. The page is not cached. The kernelet's ext2 issues a block request to its virtio-blk front-end, which fills a descriptor chain in its own queue memory (frames from the kernelet's grant) and writes the notify register of its `IoMem`: **one crossing**, a function call into the host backend on this thread, in a host scope, after the stack check. The backend walks the chain, checks each frame's owner tag (7's), bounds the request, and submits a host block request against the extent 7's handle maps to, with 7's frames as the DMA target. The thread parks by name. The physical driver completes; the host's completion path writes the used ring into 7's frames (owner-checked) and posts 7's block-interrupt job; 7's worker runs the front-end's completion routine, which wakes the parked thread by name. The thread returns into the page cache and copies the page to `buf` through a `VmWriter` on its own `VmSpace`. If `buf` is not resident, the copy faults in kernel mode, the host's injected handler enters `KerneletEntry::page_fault` on this thread under its own catch, the kernelet maps the page under a cursor, and the copy resumes. Two crossings in all, both function calls.

If kernelet 7 is killed between the notify and the completion, the epoch has advanced, the drain in [step 4](faults/destroy.md) waits for this request, the completion still writes 7's used ring (the frames are 7's until [step 8](faults/destroy.md)) but its job is refused, and the parked thread is evicted with a cancellation and terminated at the park's return.

## A vsock message from kernelet 3 to kernelet 7 {#vsock-message}

A process in kernelet 3 calls `send(2)` on a connected `AF_VSOCK` socket. Kernelet 3's vsock front-end calls `rref_new::<DataPacket>` (one crossing), charged to 3's channel account, and copies the user bytes into it. It calls `send(rref)` (one crossing): the host checks the connection, checks 7's posted credit, flips the row's owner from 3 to 7 and moves the charge, pushes the `RRef` onto 7's worker queue for this connection, posts 7's job. Kernelet 3 no longer has a name for the buffer; the compiler saw to that. Kernelet 7's worker, at the top of 7's group, drains the queue in a batch and hands the packets to 7's socket layer; a `recv(2)` copies the bytes out and drops the `RRef`, which releases the frames and refunds 7. Nothing in the kernel copied the payload. If kernelet 3 dies after `send`, nothing happens to 7's packet: its owner is 7.

## A panic in `ioctl`, and a kernelet that will not stop {#panic-and-spin}

A tenant in kernelet 12 finds an `unwrap` in an obscure `ioctl` and triggers it. The panic unwinds through kernelet frames to the trampoline (about 2.8 µs plus 840 cycles per frame in a model), releasing 12's own locks on the way; the catch kills the thread and charges one oops to 12's budget. Nothing outside kernelet 12 noticed. The tenant does it 200 more times; at 12's budget the host marks 12 dying, and 12's threads are terminated at their next quiescent points.

Another tenant, in kernelet 9, spins in a syscall with a kernelet spin lock held. Its preemption count is nonzero and its host lock depth is zero. After three ticks the tick handler marks 9 dying and rewrites the interrupted frame to land in the [landing function](faults/tiers.md) on return from the interrupt; the CPU is free 3 ms after the spin began, no host structure is inconsistent, and kernelet 9's destroy proceeds. Had the tenant been inside a `vmar` operation, the cursor's lock depth would have been nonzero and the kill would have waited for the end of that 2 MiB chunk.
